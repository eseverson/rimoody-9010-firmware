# Android Auto on the head unit

Status 2026-10-31: research; decision made (below). Sources: the 16 MB NOR dump (`dump1.bin`), eCos strings, the module filesystem below.

## What the stock firmware has

- **A real Android Auto implementation**, wired and wireless, as a loadable module: `android_auto_ROM.bin` (module_android_auto 2.1.0, version.json 2.1.159a, dated 2024-07-08). Decompressed it is 312848 bytes of NDS32 code with PolarSSL (built from `/home/lingyu.yan/module_core/external/polarssl`), the AA control protocol (`CONTROL_MESSAGE_TYPE__MESSAGE_ENCAPSULATED_SSL`, `AASslWrapper`), and an embedded PEM certificate and private key (the head unit's Android Auto identity).
- **Sibling modules** in the same filesystem: `airplay`, `carplay` (+ `iap2`), `carlife`, `autolink` (third-party mirroring app `com.link.autolink.pro`), `vautolink`, `wfd` (Miracast).
- **Hardware H.264 decode** driven by eCos (`h264/h264_vid.c`: `h264_create`, `h264_trigger_decode`, `H264_SpmpProgramStoreReg`, SPS/PPS/slice parsing in software, decode in hardware). Phone projection video goes through it.
- **USB accessory (AOA) host side** in eCos (`aoa_init_accessory`, `aoa_bulk_*`, "AOA::starting device in accessory mode").
- **Audio**: the AUDIF track API used by AA/CarPlay audio (notes/audio.md).

## Where it lives in flash

- Two JFFS2 filesystems (magic 0x1985, no compression at the JFFS2 level): 0xB40000 (config: `0.bin`, `0_v.bin`, `ir.bin`, `key.bin`, `tp.bin`, `usercfg.bin`) and **0xB60000 (projection modules)**, one directory per module with `<name>_ROM.bin` + `version.json`.
- Each `_ROM.bin` is LZMA-alone (props 0x5D, dict 8 MB). All but `android_auto` are XORed with one byte (airplay/carplay/wfd 0x4D, autolink/carlife 0x1D, iap2 0xCD, vautolink 0x6D).
- Extraction: a small JFFS2 parser (jefferson stops on repeated node versions), then de-XOR + `lzma.decompress(FORMAT_ALONE)`. Extracted copies are kept out of git (scratchpad), since they are vendor code and contain the AA private key.

## Can our firmware host the vendor module?

No, not in practice. Inside the module every `sethi/ori` call (3795 calls, 603 targets) stays within the module; calls into eCos are PC-relative `jal`, so the module is linked for one load address next to one exact eCos build. Hosting it means providing eCos's functions at eCos's addresses, i.e. running eCos.

## Options

| | What | For | Against |
|---|---|---|---|
| A | Our firmware for everything else; reboot into stock eCos for Android Auto | Works today (vendor AA, licensed cert, HW decode, audio) | Seconds of switch time; two systems; our UI is gone while AA runs |
| B | Run our code inside stock eCos (as a module like the `_ROM`s, or a task) instead of replacing it | AA, audio, video, radio keep working; our UI/apps on top | Not the "full replacement"; tied to closed eCos |
| C | Own Android Auto in our firmware | Fully ours, one system | Needs, all ours: USB host on the phone port + AOA, TLS (mbedTLS), the AA protocol (protobuf channels: control, video, audio, input, sensors), the **H.264 hardware decoder reverse-engineered** from eCos, audio output (DSP microcode, notes/audio.md), and a head-unit certificate |

The certificate for C: Google's phone app only talks to head units presenting a certificate signed by Google. The only one available is this unit's own (embedded in its AA module). Using it in our firmware on this same unit is the owner's call.

## Decision (owner, 2026-10-31)

**C: our own Android Auto stack, using this unit's certificate.** The embedded certificate is Google's reference head-unit certificate (subject O=Google-Linux-Reference, issuer O=Google Automotive Link, RSA-2048, sha256WithRSA, valid 2014-08-12 to 2044-08-11), with the Google Automotive Link root (2014-06-06 to 2044-06-05) and one private key. The key and certificate stay out of git and out of the payload image: the payload will load them from the SD card at runtime.

## Wireless only (owner, 2026-10-31)

USB Android Auto is not wanted, only wireless. How wireless AA works: the phone pairs with the head unit over Bluetooth, finds the AA wireless RFCOMM service (UUID 4de17a00-52cb-11e6-bdf4-0800200c9a66), and over RFCOMM receives the head unit's Wi-Fi access point (SSID, password, BSSID, security) and an IP/port; it joins the AP and opens a TCP connection, and from there the AA protocol is the same as over USB (same framing, TLS, channels).

The stock firmware does exactly this on this hardware: hostapd with the RTL8188F in AP mode (2.4 GHz; the chip has no 5 GHz) and an RFCOMM interface to the Bluetooth chip (`RFCOMM_IF_sendData`; the AA module's `AABluetoothEndpoint` / `AAWifiDiscovery` / `setWiFiInfo` / `setWiFiIPAndPort`). So 2.4 GHz wireless AA is accepted by phones, at least the ones the vendor tested.

Consequences for the plan: the USB phone port and AOA work is dropped (`test/aa_host.c` stays only as a protocol harness); `aa.c` is transport-independent and stays. New pieces:
1. **Wi-Fi AP mode** on our RTL8188F driver: beacons, probe/auth/assoc responses, a WPA2-PSK authenticator (the 4-way handshake from the AP side; wpa.c has the supplicant side), and a DHCP server for one client. Reference: Linux rtl8xxxu gained AP mode for the 8188F.
2. **TCP**: lwIP (raw API, in the net task) on a netif over our 802.11 data path, replacing ip.c's hand-rolled UDP/ARP/ICMP; HU1 moves onto it.
3. **Bluetooth RFCOMM** through the Jieli AC6965A: how eCos registers the AA service and moves RFCOMM data over the chip's link (being mapped). The Jieli's own firmware does the Bluetooth stack; we only get what its UART protocol exposes.
4. Decoder and audio as before.

## eCos maps (Haiku passes over ecos.ann.dis, 2026-10-31; addresses are eCos load addresses; not yet checked by hand)

### Phone USB / AOA
- AOA switch (0x444E9A): GET_PROTOCOL (0xC0, 51, len 2, 500 ms; version <= 0 aborts), SEND_STRING (0x40, 52, wIndex 0..5, string incl. NUL), START (0x40, 53, **wValue 1**). Strings: "Sunplus, Inc." / "DVD" / "Autolink" / "2.0" / "http://support.autolink.top/Autolink.apk" / "0000000012345678" (an alternate set can come from a pointer table at 0x6E298C). No request 58 (audio) here.
- After re-enumeration: VID 0x18D1, PID 0x2D00..0x2D05 means accessory mode (0x444D7E); a device already in that range is not switched again.
- Port gate: "accessory not support on port[%d], accessory port[%d]" compares the port with a global (0x6E2BC8); which EHCI the phone port is stays open: check PORTSC of EHCI0 (0x9C102164) with a phone plugged in.
- Apple devices (VID 0x05AC) take a host-mode branch with a role switch (0x4447EE); not needed for AA.
- `usb_vbus_ctrl(port, on)` 0x45A390 through a registered function pointer; GPIO unknown.

### H.264 decoder ("MFD", multi-format decoder, with an "SPMP" sub-processor)
- Entry: `mfd_if_init` 0x430E38, `mfd_if_reset` 0x430D44, `mfd_if_deinit` 0x430F42; `h264_create` 0x436AE0; per-codec dispatch 0x432F9A; `h264_trigger_decode` 0x4147AE; `real_decode_h264_video` 0x4135EA (4.3 KB).
- Registers 0x9C00C000..0x9C00Exxx. Status 0x9C00DC84 bit 0 ("wait picture end"). Doorbell: 0x9C00D550 = 0x1F8, wait bit 0; poll 0x9C00D570 bit 0 (done, ~500 tries, "spmp processing done timeout"); then 0x9C00D570 = 1, 0x9C00D550 = 0; 0x9C00D558 carries an argument. Config block 0x9C00D640..0x9C00D72C (written at 0x4158A8).
- Software parses SPS/PPS/slice headers (0x43B3C4..0x43C5C0, 0x43DE28). `H264_SpmpProgramStoreReg` 0x43A602 builds a command ring of byte-swapped words in the decoder context (register IDs like 0x04060000, 0x04200000..0x04300000); how the ring reaches the hardware is open.
- Frame buffers: luma/chroma address/scan-type programming in 0x42D674; allocation 0x43815C / 0x4330E4. Display likely through the 0x9C150xxx block via the "AV broker" 0x3CF114. Output format unknown.
- No microcode download found yet; whether the SPMP runs loaded code is open.

## Bluetooth RFCOMM through the AC6965A (Haiku map of eCos, 2026-10-31, unverified)
- RFCOMM runs over the same MCU link as `AC`-prefixed frames (built by 0x31DDF8, sent through 0x31D6D4 / McuCmd). **`ac` is on the banned-frame list: nothing sends an AC frame without the owner's explicit go-ahead.**
- Out: `RFCOMM_IF_sendData` 0x388918 splits payloads into 50-byte chunks, `AC 2a <len> <handle> <data>` for all but the last, `AC 2b <len> <handle> <data>` for the last (50 ms between chunks).
- In: chunks `[len][data]` collected by 0x385EA2 (`RFCOMM_DATA_PARSER_IND`) / 0x385EF2 (`END`) into a 256-byte ring; channel state 2 (AA, set beside "wifi AndroidAuto on") hands them to the AA middleware. The inbound frame type that carries them is not identified yet.
- Connect event (0x3866EC `RFCOMM_CONNECT`): rfc_info +0x0A handle (u32 LE), +0x12 the 16-byte service UUID; the AA UUID constant sits at 0x6C021C. No SoC-to-chip frame carrying the UUID was found: the Jieli firmware probably advertises the AA service itself. After connect eCos sends `AC 29 04 <handle4>`.
- Stock AA TCP endpoint: IP 192.168.0.1, port 8765 (0x3927C8).
- Other BT commands go through a selector (0x3887D0) using a flash table near 0x984ACE80; its layout is not decoded yet (the bytes there are 8-byte index/value pairs).
- Next: watch the MCU link (receive only) while a phone pairs and starts wireless AA under stock firmware, if the stock firmware can be booted with our UART tap; otherwise decode the inbound dispatch.

## Bluetooth on this unit: the AC6965A never starts its Bluetooth side (2026-11-02)

- Owner: under the stock firmware the unit never shows up in a Bluetooth scan, even on the stock Bluetooth app's connect screen, with the SD card removed and from a fresh boot. ACC is connected.
- Two stock-boot captures (`tools/ecos_snap.py card-bt` / `show-bt`: stubs over eCos's dead `pwm` handler log every frame through the MCU frame builder 0x521aa8, the RFCOMM event handlers, and the prints of the 0x380000..0x39ffff code; 3 minutes each, the second with the owner in the stock Bluetooth app) show **no `AC` frame at all**. eCos sent only `ed 8c`, `11 00`, the time reply `a1`/`a8` to the MCU's `a4`, backlight `ee`, `11 01`, `e6 00`, mute `01 01` / unmute `01 00`. Opening the Bluetooth app only printed "bt get local name" (eCos's stored name, `CAR-BT-5639`, in its settings block at flash 0xFFE719) and `btap_audio_switch on:0`.
- Why: Bluetooth events reach the SoC as MCU frames tagged `AC` (MCU RX dispatch 0x31e476: tag 0xA1..0xAC; `AC` → `bt_parse_receive` 0x387c48, which looks up event byte 0 in the flash table at 0x984acc84: 0x0b BT_INIT 0x386ea4, 0x18 RFCOMM_CONNECT 0x3866ec, 0x19 RFCOMM_DISCONNECT 0x386394, 0x1a RFCOMM data 0x385ea2, 0x1b data end 0x385ef2, ...). eCos does all of its Bluetooth setup only after the chip's `BT_INIT` event (which also needs the `a4` handshake flag 0x71e5a6 set; it was). The chip never sent `BT_INIT` or any other `AC` event, so eCos never sent it anything either. The board has a PCB antenna next to the AC6965A, so this is not the harness.
- No AC6965A firmware image is in the NOR flash (only the file names MCU_SY260L.BIN / UPG_MCU_CMD for a card update), so the chip's own firmware cannot be checked offline.

## Bluetooth static analysis: the MCU is the AC6965A, and Bluetooth worked under stock on 2026-10-31 (2026-11-02)

Static analysis only (eCos disassembly, `dump1.bin`, the logic-analyzer decodes kept in the first session's transcript, the teardown doc). Nothing was sent to the unit.

**Q1, what the "MCU" is: one chip, the AC6965A (high confidence).** The 28-pin SOP next to the PCB antenna is marked `AB24C099140-65A4` (Jieli marking for an AC6965A with 512 KB internal flash, teardown doc). The MCU frames (`a1` RTC tick, `a2` ACC, `a5` firmware build "Oct 8 24 11:58") and the Bluetooth frames (`ac`) were all captured on that chip's own pins 3/4 (UART on its USB pins, 115200). eCos's MCU firmware updater streams `MCU_SY260L.BIN` over the same UART1 link and prints `-->Ac6965A_Mcu Upg end!` (0x4763fa). `SY260L` matches the board name `7388-2900-260L`. So there is no separate Bluetooth chip behind an MCU. Bluetooth and system control run in one Jieli firmware, and a dead or unpowered Bluetooth chip is ruled out: the same die answers every MCU frame.

**Bluetooth did work under stock eCos (high confidence; decoded captures, zero framing errors).** These are captures from the first session (transcript `~/.claude/projects/-home-evan-workspace--electronics/a24f2195-...jsonl`, lines 2749, 2802, 2840 and 2940, taken 2026-10-31 02:19Z to 02:55Z, before any SD ISP round or NOR patch):

- Owner's Pixel 10 Pro (`digital-connect.csv`, ~70 s): `ac 18` (RFCOMM connect with the AA UUID 4de17a00-52cb-11e6-bdf4-0800200c9a66), `ac 10` ("Pixel 10 Pro" + its address), then the full wireless AA handshake in `ac 1b` / `ac 2a` / `ac 2b`, then AVRCP metadata `ac 15 01/02/03`. A later capture (~200 s) was on pure Bluetooth audio.
- `dump1.bin` (read 2026-10-12) already holds the generated name `CAR-BT-5639` at 0xFFE719. eCos makes that name only after a BT_INIT (below), so the chip had reported BT_INIT before 2026-10-12 as well.
- This fits the owner's observation: the phone was already paired and connected without the unit ever showing up in a scan. "Connectable" is shown; "discoverable" was never seen.

**Correction to the 2026-11-02 section above: BT_INIT is event 0x0a, not 0x0b (verified by hand).** The event table at flash 0x984ACC84 has 8-byte entries `{u8 event, 3 pad, u32 handler}` (`bt_parse_receive` 0x387c48 compares byte 0 and calls `[+4]`): 0x0a → 0x386ea4 (BT_INIT, prints "--->BT_INIT BResetFlag:%d"), 0x0b → 0x3873c8 (unnamed), 0x10 → 0x387002, 0x18 → 0x3866ec, 0x19 → 0x386394, 0x1a → 0x385ea2, 0x1b → 0x385ef2. The handler takes the 6-byte MAC from `ac 0a` (0x71eb37..0x71eb3c), returns early if the a4 flag 0x71e5a6 is 0, then calls 0x385380 → 0x38538c, which builds or loads the name and sends it as selector cmd 0x22 (`ac 19`). The ~8 s from BT_INIT to `ac 19` in the capture matches the two 5 s sleeps in 0x38538c.

**BT_INIT is a one-shot, sent by the chip about 5 s after its own power-up, whether or not the SoC talks to it (high confidence).** Chip `e0` → `ac 0a`: 4.92 s in the good boot, 5.07 s in both stalled boots of `digital.csv` (266.775 → 271.845 and 301.881 → 306.951), where the SoC never sent a frame. It was not repeated in any later capture. When the MCU cuts the SoC's power itself (the ~145 s reset, update parking), the chip keeps running and sends no new BT_INIT.

**Leading hypothesis H3: the SoC is not listening when BT_INIT goes out (unverified; most promising lead).** In the good stock boot, eCos had UART1 running about 1.5 s before the chip's BT_INIT. Every observation since then has a later or different SoC start:
- Our NOR boot script (written 2026-10-31, before the 15:06 local cold boot) now runs before eCos: pinmux, UART1, `d1 00`, xboot's SD setup, `mmc dev 0`, `fatload` and only then `bootsp`. With no card, the `mmc` and `fatload` failure time is added in front of eCos. It needs to be at least ~1.5 s for eCos to miss the BT_INIT, which is plausible but not measured.
- The two `card-bt` / `show-bt` captures started eCos from our payload (`ecos_boot_check`, `ECOSRUN.LOG` says `at t=7679 ms` of U-Boot time, plus the 4 MB image load and eCos init). eCos's UART was up long after a power-on BT_INIT. If the run followed an MCU power cut rather than a plug cycle, there was no BT_INIT at all. **So those captures cannot tell "the chip never sends BT_INIT" from "it was sent before eCos listened".**
- Our payload logs MCU bytes from about 5.9 s (U-Boot timer; first log line `mcu: 5939: ...`, 2026-10-31 22:06Z). That is at or just after the BT_INIT window, and that boot followed an MCU power cut anyway (no BT_INIT expected).
- The `AC 30` / `AC 19` probe getting no reply is weak evidence: in the good capture the chip never answered `ac 19` either, and nothing shows that `ac 30` gets an answer.
- If H3 holds, eCos with the stock boot timing would see BT_INIT again, and our payload only has to receive it (or be listening when the chip boots) and then send the name. The allowed `AC 2a/2b/29 04` RFCOMM path would then be usable with no extra hardware.

**Other hypotheses (unverified):**
- H1, the chip is latched in a state with Bluetooth off. Between the last good capture (02:55Z) and the NOR patch, eCos ran its "dvd upgrade start" path (0x47539c: save settings, then **`e5 01`** via 0x31dcca) to start the SD ISP rounds, and the MCU then parked (link pins low, ignored `d1`/`e5 00`/`ad`) and cut power after ~145 s. Stock expects U-Boot's `ispsp update_finish` (`ad`) after a real update. A persistent "update pending" flag in the Jieli firmware that keeps its Bluetooth stack off would explain everything too. No way to check this without the chip's firmware.
- H2, damage to the Bluetooth part of the chip from probing its 0.635 mm pins on 2026-10-30/31. A dead antenna path would not stop BT_INIT, so this would have to be the Bluetooth controller itself, while the rest of the die keeps working. Least likely.
- `a4` changed from `a4 01` (good boot, the chip had just powered up) to `a4 00` in every later log. In eCos (0x31e0ec, "ProcessReceiveMemory") a nonzero value sets 0x71e5a6 = 2, sets the reconnect flags 0x6de205/0x6de206 and clears two saved bytes; 0 sets 0x71e5a6 = 1 and reloads three 0x30-byte Bluetooth records (0x38528c). Either way BT_INIT is accepted. Probably "the MCU just powered up" against "the MCU was already running"; unverified.

**Q2, a configuration or factory gate on the SoC side: none found (medium-high confidence).** `user_config` (RAM 0x7340ac, loaded from `/test/usercfg.bin` in the JFFS2 at 0xB40000 by 0x55dcee, dumped by 0x55d9f4) has `btcfg.flag` (+0x00: 1 = use `btcfg.btname` at +0x01 instead of the generated name; 0 in `dump1.bin`), `setupcfg.*` and `factorycfg.{auxin, brightness, dtv, ir_type, navi, radio, rcam, rds, sd, tv, can_bus, tft_panel_*}`. There is no Bluetooth enable or module-type field. A factory menu exists (`factoryview` / `FactoryViewInit` 0x34f0ea / `FactoryExec` 0x3506ac / `passwordview` 0x33fbc8); its item list and password were not decoded (UI resource tables). The MCU RX dispatch (0x31e476, jump table 0x31e4a4: a1 0x31e2b6, a2 0x31e07e, a4 0x31e0e8, a5 0x31e41c, a8 0x31e33e, ac → 0x387c48) passes `ac` frames on unconditionally. The BT_INIT handler checks only 0x71e5a6, 0x71eb5d and 0x71eb1a, all runtime state. The settings block around 0xFFE719 holds only the name (0x1c bytes); the bytes before it are zero, and an EQ-like table follows at 0xFFE73B. No SoC GPIO for Bluetooth power or reset was found. The AC6965A controls the SoC's power, not the other way round. The Bluetooth code range was not searched exhaustively for GPIO writes.

**Q3, the boot frames (verified senders):** `d1 00` heartbeat (0x31d738); `ed x` 0x31d8b0, x = `user_config`+0x54 (0xff → 0x73) at MNSystemInit (0x31f812), elsewhere from a {0x0a, 0x4b, 0x78} table (0x32fbe0) or 0x6dd81d; some level, not Bluetooth (unidentified); `11 x` 0x31d98a = the SoC power state (0x71e5a2; `11 01` after the a4 reply and in power_on 0x47af0a, `11 00` on power-off 0x47adfc); `e6 00` 0x31db54, one caller (power_on), always 0; `ee x` backlight duty (0x31d928); `01 x` mute; `e5 x` 0x31dcca (`e5 01` before a SoC update, `e5 03` MCU firmware update); `ad` 0x31db32 = reboot request after saving (factory reset, settings restore, update); `e8 01` shutdown ack. None of them takes a Bluetooth setting, so none can turn Bluetooth on under a different configuration.

**Q4, the MCU update path (analysis only; never to be run without the owner's explicit approval).** `mcu_upgrade_init` / "check upgrade" (0x475b8e) looks for `MCU_SY260L.BIN` (also `LOGO.BIN`, `DKEY.BIN`, `ISP_UPDT.BIN`). 0x476270 ("McuUpgrade dwSize") sends **`e5 03`** (0x47631c; the only other `e5` caller is the `e5 01` above), drops UART1 to 9600 (0x521df6(0x2580)) and runs a state machine on packets starting with 0x55 (0x475f32). `UPG_MCU_CMD` 1 switches to 230400 (0x38400); 2 carries a 4-byte address and a 4-byte length, and the SoC sends that slice of the file (0x475e7c); 3 ends ("Ac6965A_Mcu Upg end!"). This is the chip pulling its own image by offset, as in Jieli's UART update module (start / read / end). That matches a Jieli SDK application with the stock update loader, so the file would be a Jieli upgrade image (likely the `.ufw` format; inference). No copy of the file is in the NOR flash.

## Reconnect after power-up: `ac 30` (2026-11-06, issue #13, build 20261106-222302, persisted)
