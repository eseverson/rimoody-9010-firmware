## Corrections to h264_decoder.md section 5

- The handoff body is entered at 0x52a6d4 (`bnez $r0, 0x52aaa6`, body when r0 == 0) from 0x5272bc in `f_005270de`; chain 0x52925e -> 0x5270de (BG2D rewrite) -> 0x52a6d4.
- `hal_vpp_init` clears bits 0..4 of 0x9C005788 before `|= 0xE0`; 0x9C0057BC is a read-modify-write (bits 3:2 = 1, 5:4 = 1, 1:0 = 0), not "= 0x14"; 0x9C005D84 also clears bits 9 and 12.

## hal_vpp_init (0x529d66..0x52a132), in order

1. Picture-quality / post blocks, purpose not decoded (read-modify-write unless "<-"): 0x9C006080 set b0, clr b1 b2 b3, set b4, clr b5; 0x9C0060A4 clr b0 b1; 0x9C0060A8 <- 0x10; bytes 0x9C0060AC / 0x9C0060AD <- 0x80; 0x9C006F80 <- 1; 0x9C006F84 <- (arg0 < arg1); 0x9C006FC8 <- 0x7F; 0x9C007000 set b0, b12 <- (arg0 < arg1); 0x9C007004 <- 0x3FF; 0x9C009A00 clr b2, set b1 b0; 0x9C009A04 clr b8 b0; 0x9C009B00 set b0, clr b2, set b4; 0x9C009B80 set b0, clr b4, set b5; 0x9C009C00 set b0 b2.
2. Scaler: 0x9C005D80 <- 1; 0x9C005D84 set b4 b6, clr b9 b12.
3. 0x9C005A80 set b0 b1, clr b6, set b8, clr b9..b13. Then 0x9C005B34..0x9C005B50 <- 0x1807, 0x6F0, 0x8FE, 0x4555, 0xA, 0x5014, 0xFF0C, 3 (looks like a YUV->RGB matrix; not decoded).
4. DDFCH: 0x9C005780 <- 1 (enable); 0x9C005784 <- 0x5E000; 0x9C00578C <- 0xD6D6D6; 0x9C005790 <- 0x3DEF.
5. 0x9C0057DC: set b0, set b4, clr b5, clr b8 b9, [17:16] <- 1, clr b24 b28 b29.
6. 0x9C0057BC [1:0] <- 0, [3:2] <- 1, [5:4] <- 1; 0x9C0057E0 <- arg0; 0x9C0057E4 clr b0..b3, set b4, clr b5 b6.
7. 0x9C0057F0 <- 0x80801021: test pattern ON (b0 enable, [5:4] pattern 2 = solid; bytes 1..3 Y/Cb/Cr). 0x80801011 = color bar.
8. 0x9C005788 clr b0..b4, set b5 b6 b7; 0x9C0057B0 / B4 / B8 set b0 and b16.

## Per frame

- Fetch geometry (0x52a1f8): 0x9C0057DC b8/b9 = H/2, H/4 predecimation; [17:16] = 1 (2 for the other format); b0 = struct+4; **0x9C0057D0 = pitch** (eCos ALIGN(width,128); ours is 1920, the decoder's BG2D pitch slot); 0x9C0057D8 = origin x [12:0], y [27:16]; 0x9C0057D4 = width [12:0], height [27:16].
- BG2D for display (in 0x5270de): byte 0x9C00A382 = ALIGN128(width)/16 (pitch slot 2), luma and chroma entries get gp = 2 and the picture's scan type; address field = phys >> 10. (We could instead point VPP0 at the decoder's own entries, gp 1, pitch 1920.)
- Handoff, index mode (0x52a7bc, confirmed): 0x9C005784 b28 <- 0, b20 <- 1; 0x9C005798 / 79C / 7A0 <- luma BG2D index, 0x9C0057A4 / 7A8 / 7AC <- chroma index (raw, not shifted). Physical mode instead: b20 <- 0 and `phys >> 10` in the same registers.
- Then: 0x9C005784 b10 <- struct+8, b21, b8 from a mode table (0x6BAEEC + mode*0x60); 0x9C0057DC b4, b5, b28, b29 from the mode (0xB = progressive: b5 = (s+4 > 0), others 0); 0x9C005788 b2 <- 0, b3, b4 <- 1; 0x9C0057BC fields from the table; 0x9C0057B0/B4/B8 set b0 b16; 0x9C005A80 b8, b9, b12 from the mode, **0x9C005A80 b0 <- 1 (commit)**; 0x9C005D84 b9.
- Scaler (0x529b06): factor `((in-1) << 22) / (out-1)`; 800 -> 1024: H = 0x31FC7F -> 0x9C005DCC (low 16) / 0x9C005DD0 (bits 24:16); 480 -> 600: V = 0x332DBA -> 0x9C005E04 / 0x9C005E08; filter index into 0x9C005DC8 [7:4] (3 for H <= 1.0) and 0x9C005E00 [7:4] (2 for V <= 1.0); 0x9C005D84 b0 b1 <- 1, b2 <- (in_w != out_w), b3 b4 <- (in_h != out_h).
- DMIX (0x523ab8): mode fields at 0x9C006C84 bits [2i+1:2i]; eCos sets both VPP0 and OSD0 to mode 0. Under U-Boot VPP0 is in mode 1. Meaning of the modes not decoded.

## SP7021 driver as a reference (2026-11-01)

Sunplus's SP7021 Linux display driver (BPI-F2S BSP on GitHub: BPI-SINOVOIP/BPI-F2S-bsp, `linux-sp/drivers/media/platform/sunplus/display/sp7021/`: disp_vpp.c, reg_disp.h, disp_tgen.c, disp_dmix.c) shares this chip's display register design:
- **DDFCH** (SP7021 G185; here at 0x9C005780, eCos's block) register by register: 00 latch_en, 01 mode_option (0 NV12, 0x400 NV16, 0x800 YUY2), 02 enable (SP7021 writes 0xD0), 03 urgent thd, 04 cmdq thd, 06..08 luma base (>>10), 09..11 chroma base, 15 frame_id, 16 free_run_control, 20 frame size (pitch), 21 crop size (h<<16|w), 22 crop offset, 23 config_0 (SP7021 0x10000), 24 config_1, 26 checksum, 27 error flags, 28 BIST (SP7021 0x80801002 = off), 29 AXI info. SP7021 feeds a linear NV12 frame by physical address.
- **TGEN** at 0x9C006A80 (G213) matches: U-Boot left config 3, user mode (reg 4 = 0x130001), 1344 x 635 total, 1024 active, start line 30, VPP0 timing adjust in reg 23 bits 13:8 = 0x10. SP7021 uses config 7 (latch mode).
- **DMIX** G217 at 0x9C006C80 matches; reg 7 (0x9C006C9C) is an output checksum (reads 0 while VPP0 is shown opaque: the mixer gets zeros).
- SP7021 has a VPOST block (G199) between VPP and DMIX; **0x9C006380 is not mapped on this chip** (reading it raised a bus error and reset the unit), so this chip's VSCL (0x9C005D80) plus the 0x9C006080 / 0x9C006F80 / 0x9C007000 / 0x9C009Axx blocks take that place.

Tried without success (panel stays green, DDFCH error flags 0x7EC = 0x220 constant, checksum 0x7E8 = 0): the SP7021 ddfch_setting on a linear NV12 color-bar frame at 0x04E00000 (`hu.py vpp linear`), enable values 0x00..0x1D0, mode 0 / 0x5E000, clock ID 0x5B on, TGEN latch mode (config 7). So DDFCH never starts. Candidates left: whatever drives the DDFCH frame start on this chip (the field-end ISR's 0x9C003080 block writes, value 0x8095 into 0x9C00308C, look like a DMA kick), the 0x7B0..0x7C0 registers (eCos sets b0 and b16 of 0x7B0/B4/B8), and the meaning of error bits 5 and 9.

## Reset bisect (2026-11-01, build 20261101-135534, hardware reset before each try)

DDFCH error flags 0x7EC stay 0 for: nothing, scaler only, the full eCos init (init_fetch), and full init + index-mode decoder picture with gp-2 BG2D entries + DMIX opaque + commit. ## Working fallback: video through OSD0 (2026-11-01, build 20261101-140144) — confirmed on the panel

`osdvid.c` (HU1 op 25, `hu.py osdvid show|on|off`): the CPU de-tiles each decoded picture (16-pixel runs, byte-swapped 8-byte groups) into a linear YUY2 buffer that OSD0 scans with its own region header (SP7021 OSD format 4, header byte 0x15 = 4), 800x480 centered, two buffers flipped through the header's data address. Owner confirmed correct SMPTE bars, then smooth motion from a live AA stream (tools/aa_phone.py, testsrc2 at 30 fps): 1800 frames, 0 decode errors, 17.9 fps end to end because the conversion (37 ms per picture, mostly the 768 KB of stores) runs inline in the net task. Next: faster conversion (fewer cache-maintenance loops, word stores) or dropping display frames when behind, so decode and network keep full rate.

### 1. What starts DDFCH

- `f_005276d8` (confirmed) is the VPP start: if the state word 0x704464 is 1 it becomes 2, the old state goes to 0x704460, the frame slots 0x704328/0x70432C are set to -1, bytes 0x7042FC and 0x704458 are cleared, then `0x52a134(0, 2, 1)` and `0x52a134(0, 3, 1)`. `0x52a134(vpp, sel, v)` is a 6-way switch (byte table at 0x52a154, cases confirmed): 0: 0x9C005780 = v; 1: 0x9C005A80 b1 = v; 2: 0x9C005D80 = v; 3: 0x9C007000 b0 = v and 0x9C006F80 = v; 4: 0x9C009A00/9B00/9B80/9C00 b0 = v; 5: 0x9C006080 b0 = v. So "start" is only VSCL on plus the 0x9C007000/0x9C006F80 block on; the stop `f_0052774c` writes the same two with 0 and calls the pattern function with id 0xD (BIST on, solid, colors kept) to blank. All of these bits are already set by `init_post`/`init_fetch`.
- The field-end ISR `drv_vpp_field_end_early_isr` (0x528b14, callers enter at 0x528b10) is queue management: `check_if_updating_current_frame` (0x528c5c), `try_to_update_current_frame` (0x52905a), the CVBS cur_wid/cur_rid/cur_r_fid reads (0x52bf80), then the BG2D rewrite and handoff through 0x5270de (0x52925e). The callees that were open: 0x5272c2 and 0x5272ec push/pop the released-frame rings at 0x70437C and 0x704360 (RAM only; "Pusing frame to released queue is failed" at 0x52730a); 0x52acd4 is the entry of 0x52acda, a picture-quality table loader (0x9C009A08..0x9C009BE4 and 0x9C006084..0x9C00609D from the tables at 0x731878.., only when a dirty bit in 0x731870 is set); 0x52abf0 toggles the PQ block enables (0x9C009A04 b8/b0, 0x9C009B00 b2, 0x9C009B80 b4, 0x9C006080 b1, each followed by 0x9C009C00 b2); 0x5268ee is the entry of 0x5268f2, per-frame geometry (0x52a1f8) followed by `0x52abc8(vpp, 0)` = 0x9C007000 b12 = 0 and 0x9C006F84 = 0 in the non-rotated path (0x526d2a..0x526d3a). After the first real frame the ISR calls `0x52b7a4(0, 0)` (0x5292d4): pattern off = 0x9C0057F0 b0 = 0, 0x9C005D84 b7 = 0, 0x9C007000 b20 = 0, 0x9C006F88 b0 = 0 (0x52b7b8..0x52b7e4). Nothing in the ISR starts DDFCH beyond the handoff vpp.c already does.
- 0x9C003080 is not a DMA kick. It is an STC, the 90 kHz system time counter (SP7021 STC_AV1 is G97 = 0x9C003080). 0x522a72, called from the ISR at 0x528b78/0x528c46/0x529044/0x529288 with a 64-bit PTS, writes +0x1C = 0, +0x0C = 0x8095 (divisor 0x95 with load bit 15), +0x08 = 0, then the counter halves at +0x04/+0x00 and +0x38/+0x3C; 0x522a48 writes +0x0C = (0x95 >> (rate >> 1)) | 0x8000; 0x522a2a, 0x522aec and 0x522b24 read it. Audio/video sync only (confirmed).

### 2. Register writes from boot to the first VPP0 frame

Order (confirmed): 0x306200 → AP display init 0x50d6f8: OSD and 2dbg init (0x52eb64) → `drv_vpp_init` 0x527354 (entry 0x527350) → mixers 0..2 (0x523328) → CVBS init 0x52ba80 → TGEN 0..2 (0x52da22, reads only) → panel clocks 0x52d6f2 → scenario 0x50ba7e → mode set 0x50c7d8 → layer setup 0x50c1a8 (run from the vsync dispatcher 0x50f284 at 0x50f524) → player start 0x5276d8 → handoff every field.

- MOON. eCos writes no MOON register for the VPP itself. The panel code 0x52d870 and 0x52d9c0 write 0x9C000018 = 0x8000800 (clock ID 0x5B on) and 0x9C150098 [26:24] = panel mode; 0x52d9a4 writes 0x9C0001AC = 0x7000000 | mode << 4; 0x52d870 also sets the TTL pinmux 0x9C000100/0x10C (0x104/0x110 in other modes); the early-boot copy 0x3157dc writes the same four. OSD0/OSD1/OSD2 get fields 3/4/5 (table 0x6bb8e8 = [3, 4, 5, 7, 8]; input 0 maps to field 0). Field k sits at bits [2k+1:2k] for k = 0..6, field 7 at [17:16], field 8 at [15:14] (0x52e62c..0x52e6b0). The vsync dispatcher 0x50f284 reads field 0 (0x52dd6c → 0x52e6b8) and runs the VPP ISR only when that field reads 0 (0x50f2a0..0x50f2ce). U-Boot programs the panel timing, user mode and resets all three TGENs (0xf21492..0xf214c4). eCos's 0x52da22 only reads (mode via 0x52e508, the ten adjust fields via 0x52e59c) until the mode set above. - Diff against vpp.c. Everything hal_vpp_init and the handoff write is in `init_post`/`init_fetch`/c == 2, including 0x9C005A80 b0/b1/b8, 0x9C0057B0/B4/B8 b0|b16, 0x9C0057BC = 0x14, 0x9C005788 = 0xE0 then b4, 0x9C0057DC b0 b4 b16, 0x9C0057E4 = 0x10. ### 3. Register meanings

- 0x9C0057B0/B4/B8 (DDFCH regs 12..14, reserved on SP7021): one per base-address slot 0/1/2 (slots 0x798/0x79C/0x7A0 luma, 0x7A4/0x7A8/0x7AC chroma). eCos sets b0 and b16 of all three at init and at every handoff (0x52a9a8..0x52a9ec) and never clears them. Inferred: per-slot valid flags. Not a run bit (they are set while the panel is green).
- 0x9C0057BC = `ddfch_frame_id` (SP7021 reg 15): three 2-bit slot selectors from the mode table, +0x5C → [1:0], +0x5E → [3:2], +0x5D → [5:4] (0x52a970..0x52a9a4). Progressive 0xB gives 0/1/1 = 0x14 (fetch from slot 1 = 0x79C/0x7A8; the handoff copies slot 1 to slot 2 at 0x52a80c..0x52a820). Inferred: which slot each field or frame fetches.
- 0x9C005784 (`ddfch_mode_option`): b20 = index (BG2D) mode (0x52a7cc, confirmed; physical mode clears it); b28 cleared in both modes (0x52a76e/0x52a7c0); b10 = struct+8 & 1 (0x52a828..0x52a838; 1 in the dummy init handoff; a field flag, inferred); b21 = mode table +0x10 (0 for 0xB, 1 for the interlaced modes 6..0xA; "field mode", inferred); b8 = mode table +4 & 1 in index mode (1 for 0xB..0x10) and 0 in the physical fast path (0x52aa5a..0x52aa80). SP7021 uses only [11:10] (format). None is a run bit.
- 0x9C005788 (`ddfch_enable`): init clears b0..b4 and sets b5 b6 b7 (0x52a0ae..0x52a0ec); per frame b2 = 0, b3 = field flag (0 for 0xB), b4 = 1 (0x52a946..0x52a96e). i143's `DRV_DDFCH_on`/`DRV_DDFCH_off` write 0xD0 / 0xC0 ("fetch en" / "fetch dis"), so b4 = fetch enable (confirmed from the i143 source), b6 b7 are always-on bits of unknown meaning, b5 is eCos only. eCos runs with 0xF0; vpp.c's c == 2 path reaches that, the color-bar path c == 1 leaves 0xE0 (fetch off; i143 runs its BIST with fetch on, so that is a difference worth closing, done in `probe`).
- 0x9C005780 = `ddfch_latch_en` (SP7021 and i143; written 1 before the config in both drivers, under the same `DDFCH_GRP_EN` switch as enable = 0xD0). Inferred: shadow-register latch at vsync. If DDFCH never sees a vsync from its selected TGEN, nothing it was told takes effect, which matches every observation so far.
- 0x9C0057DC = `ddfch_config_0`: SP7021 writes 0x10000 only; eCos adds b0 (struct+4, 1 at init), b4 = 1, b5 = 0 for 0xB, b8/b9 = H predecimation, [17:16] = 1 (2 when mode table +4 == 0, 0x52a920..0x52a942), b24 = 0, b28/b29 = 0 for 0xB. 0x9C0057E0 = `ddfch_config_1` = 0. 0x9C0057E4 (reserved on SP7021) = 0x10.
- 0x9C0057EC: the BSP names only the register (`ddfch_error_flag_info`); no bit names for 5, 9 or 16 anywhere in it. Unsure. They changed only with the SP7021-style linear setup, so DDFCH is clocked and decodes its configuration; that does not prove it fetches.

### 4. Enables and muxes outside DDFCH

- VSCL 0x9C005D80 is the i143 G187/G188 block, same map: config1 +0, config2 +4, i_xlen/i_ylen +0x0C/+0x10, s_xstart.. +0x14..+0x20, o_xlen/o_ylen +0x24/+0x28, d_xstart.. +0x2C..+0x38, hint_ctrl +0x48, hfactor +0x4C/+0x50, vint_ctrl 0x9C005E00, vfactor +4/+8, checksum 0x9C005E58. i143 writes config2 = 0x221F for DDFCH input, 0x021F for VPPDMA, 0x121F for OSD0 (`vpp_path_select`): bits [13:12] are the scaler's input mux. eCos clears b12 in hal_vpp_init (0x529ee4) and never touches b13, so it runs with [13:12] = {b13's reset value, 0}; vpp.c does the same. Either b13 resets to 1 here or the encoding differs; the probe tries all three values. Also from i143 and eCos: config2 b7 = VSCL color bar, b8 = bordered (i143 0x29F/0x39F; eCos patterns 0xE/0xF, 0x52b7ca and 0x52b836..0x52b84a); b0..b4 and b9 are set by both (eCos: b0 b1 always, b2 = H scaling, b3 b4 = V scaling, b9 from the mode table, 1 for 0xB).
- 0x9C005A80 (G181, absent on SP7021 and i143): b0 = commit at every handoff (0x52aa1e), b1 set at init (0x529efc; 0x52a134 case 1 toggles it), b8/b9/b12 from the mode (0x52a9f4..0x52aa1a: 1/0/0 for 0xB). Nothing else writes the block; vpp.c matches.
- VPOST is 0x9C006080 (G193 here, not SP7021's G199, which is why 0x9C006380 bus-errors): the use matches the SP7021/i143 VPOST map, +0x24 (reg 9 `opif_config`) clr b0 b1, +0x28 (reg 10 `opif_bgy`) = 0x10, bytes +0x2C/+0x2D (reg 11 `opif_bgyu`) = 0x80/0x80 (black background), reg 0 set b0 b4, clr b1 b2 b3 b5 (0x529d72..0x529dbe); the PQ loader writes +4..+0x1D (`vpost_adj_*`). vpp.c matches.
- 0x9C006F80 / 0x9C007000: the window written by 0x52aad4 (and by U-Boot's logo path with the logo geometry, 0xf21256..0xf212cc) is the rotation window: it is enabled only when the per-frame rotation mode is nonzero; the normal path calls 0x52abc8(vpp, 0) every frame (0x52707a, 0x526d3a) → 0x9C007000 b12 = 0, 0x9C006F84 = 0. 0x9C007000 b20 and 0x9C006F88 b0 are test patterns (eCos ids 0x12 and 0x10/0x11). 0x9C007000 b0 and 0x9C006F80 = 1 are block enables set by hal_vpp_init and by start (0x52a134 case 3); vpp.c sets them. Not a candidate.
- TGEN 0x9C006A80 (G213 map, three instances at 0x6A80/0x6B00/0x6B80 for panel/CVBS/RTE). Reg 29 (+0x74) `tgen_source_sel`, per-input timing source (above), is the one register in the chain that gates VPP0 and that neither U-Boot's normal path nor vpp.c writes. Adjust regs 23..27 (+0x5C..+0x6C) hold 6-bit fields [5:0] and [13:8] for inputs 0..9 (0x52e59c); VPP0 is reg 23 [13:8], already 0x10 under U-Boot, matching SP7021's `DRV_TGEN_Adjust(VPP0, 0x10)`. Reg 1 (+4): b0 reset, [6:4]/[9:8] sync source (eCos 0/0 in the normal path, U-Boot 2/2 only when rotating). Reg 7 (+0x1C) `tgen_dtg_venc_line_rst_cnt` = 2 (eCos) or 1 (U-Boot's rotation branch). Reg 13 (+0x34) b12 = field (0x52e738).
- DMIX: layer mode = config1 2-bit fields (L1 = [1:0]); layer source = config0 [10:8] L1, [14:12] L2, config2 nibbles L3.. (SP7021 `DRV_DMIX_Layer_Init`, U-Boot 0xf21568..). Reg 26 (+0x68) [2:0] = 2 at eCos init, [5:4] = output select (0x523d60). Three mixers at 0x9C006C80/0x9C006D00/0x9C006D80.

### What this adds up to

Every DDFCH, VSCL, 0x9C005A80, VPOST and PQ write vpp.c makes is what eCos makes, in the same order, and eCos adds no clock or reset for the VPP. What is left is the plumbing eCos inherits from U-Boot or sets once in its scenario setup: the TGEN source select for VPP0 (eCos writes it, U-Boot's normal path does not, SP7021's driver zeroes it at init), the VSCL input mux [13:12] (semantics known only from i143), the TGEN0 reset pulse after programming (U-Boot does it once, we never retrigger it), and clock 0x5B (the earlier try may have switched it on after the DDFCH/VSCL writes). A DDFCH that never gets a frame start from its selected TGEN explains everything seen: no fetch, checksum 0, no error flags, a BIST that never latches (latch_en = 1), zeros at the mixer (Y = Cb = Cr = 0 is green), and no reaction to any DDFCH or VSCL write.

## Static follow-up round 3 (2026-11-01, after the unit's round-2 answer)

What the round-2 result pins down: VSCL, VPOST and DMIX run (the scaler's own pattern gives VSCL checksum 0xD86 and DMIX checksum 0x51A7, and 0x9C006AF4 already read 0), so the break is at DDFCH itself or at its hand-over to the scaler. Rechecked statically, with the result:

- The scaler routine 0x529b06 (read in full this time) writes only +0x4C/+0x50 and +0x84/+0x88 (factors) and the filter index in +0x48/+0x80 [7:4]; it reads +0x54/+0x58 (hint_initf) and never writes them or the hint/vint ctrl low bits. VSCL instances are 0x100 apart (`add_slli r0, base, vpp, #8`). So vpp.c's VSCL programming is complete relative to eCos; nothing there is missing.
- eCos's "2dbg" init 0x52ec48 (0x9C00A384..0x9C00A3B8 from two 6-word tables, all 256 entries = 0x7000000, 0x9C00A39C b5 clr / b13 b4 set) is already mirrored by `bg2d_init` in vdec.c with the same table values, and eCos's entry writers 0x52edc6/0x52ed0a/0x52ed32 match `bg2d_set`. Not a difference.
- The eCos "reset" shell command (0x31793a) pulses MOON resets 0x1F, 0x63, 0x64, 0x66, 0x67, 0x68, 0x69, 0x6B, 0x6C, 0x6F, 0x70, 0x71 (the codec cluster); the decoder clock set is 0x5A, 0x66, 0x69, 0x71 (0x422e74). No display IDs, and nothing at boot. The gated-clock helper 0x313000 is called once with ID 0xF (0x530200), not for the display.
- eCos's pattern name table (ecos.strings 14947..14961): ids 1..0xD are `DDFCH_INTER_BGC_*`, `DDFCH_INTER_BORDER`, `DDFCH_INTER_COLOR_BAR`, `DDFCH_INTER_BGC_MANUAL`; 0xE/0xF are `VSCL_COLOR_BAR` and `VSCL_BOUDARY_RING`. "INTER" = DDFCH's internal generator, which is what we drive with 0x80801011. Sunplus's own SP7021 display chapter (Confluence, "21. DISPLAY") expands DDFCH as "De-interlace Data Fetch", which explains the three address slots (previous/current/next field), the slot selectors in 0x7BC and the per-slot flags 0x7B0/B4/B8; the DMA sub-block is listed as DDFCH_VIDEO_DMAR_INFO.
- Error flags: 0x220 came with the SP7021-style physical fetch from a real buffer, 0x20220 with the BIST on plus fetch enable (physical mode, base address 0), 0 with index mode plus fetch enable. So bits 5 and 9 track "fetch enabled in physical mode", bit 17 tracks "BIST on"; index mode raises nothing. Read as read errors (bits 5/9) this says DDFCH's own DMA reads of DRAM fail where OSD0's and the decoder's (through BG2D) succeed; read as underflow it says DDFCH does get frame starts and nothing arrives. Either way the fetch engine is the suspect, not the timing.

### Round-3 probe steps (`hu.py vpp probe MASK [PATH]`, build 20261101-164030; the mask is now 16-bit, keep to five or so bits per call so the reply beats the 2 s timeout; `vpp restore` afterwards)

Each step samples the DDFCH/VSCL/DMIX checksums and the DDFCH flags; run each with bit 1 (`init`) set so the state is known. Ranked:

1. `probe 0x81` then `probe 0x41`: the handoff written inside vblank (bit 128: wait for TGEN0's line counter +0x34 to pass the field end line +0x2C, then BIST on, fetch enable, commit; the reply prints the line it fired on) and 2000 commits of 0x9C005A80 b0 about one line apart over three frames (bit 64). Tests whether eCos's commit works only because it is issued from the field-end ISR, i.e. inside vblank. If the DDFCH checksum goes nonzero on either, the commit window is the answer and the per-frame handoff has to move to a vsync-driven point (TGEN line counter poll or the display interrupt).
2. `probe 0x101` and `probe 0x201`: physical fetch with the BIST off from the OSD video buffer at 0x07A00000 (a region OSD0 scans without trouble) and from the decoder's slot 0 at 0x04600000. Compare the flags with 0x220: if both still raise bits 5/9, DDFCH's DMA cannot read DRAM at all in physical mode (bus port, address view or a missing enable in 0x784 bits 12..18); if the 0x07A00000 read is clean while 0x04600000 is not, it is an address-range or protection issue.
3. `probe 0x401`: mode_option 0x784 = 0xF000 (the reset value seen under U-Boot, bit 12 set) then 0x5F000. eCos clears bit 12; if bit 12 is an enable for the physical-address DMA path that eCos does not need because it only uses index mode, this shows it.
4. `probe 0x801`: TGEN0 adjust1 0x9C006ADC = 0x100D (i143's init value; U-Boot left [5:0] = 0). Low odds, since eCos runs with 0 there too, but free.
5. If 1..4 stay at zero, the remaining static lead is the DDFCH register bits the Sunplus SP7021 display chapter documents (fetch pending in this round's notes below); the dynamic lead is to try index mode with the decoder's own entries (gp = 1, exactly as the decoder leaves them) and a BG2D entry built for a linear buffer, to separate "index path works, physical path does not" from "DDFCH never fetches".
